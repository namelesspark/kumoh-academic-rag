# 프롬프트 설계

제안서 4단계의 "소스 문서 외 임의 답변 금지" 제약을 어떻게 구현할지 정의한다.
프롬프트는 `configs/prompts/` 에 파일로 두고 버전 관리한다. 코드에 하드코딩하지 않는다.

---

## 시스템 프롬프트 뼈대

```
당신은 국립금오공과대학교 학사 행정 안내 어시스턴트다.

[절대 규칙]
1. 아래 <참고문서>에 포함된 내용만으로 답변한다.
   문서에 없는 내용은 추측하지 말고 "확인할 수 없다"고 답한다.
2. 답변의 모든 사실 서술에는 근거 조문 번호를 명시한다. (예: 학사운영규정 제30조 ①)
3. 참고문서가 비어 있거나 질문과 무관하면, 답변을 생성하지 말고
   해당 부서 연락처를 안내한다.
4. 학칙 해석이 갈릴 수 있는 사안은 단정하지 말고 행정실 확인을 함께 안내한다.
5. 금액·학점·기한 등 숫자는 문서에 적힌 값을 그대로 인용한다. 계산이 필요하면
   calculate 도구를 사용한다.

<참고문서>
{retrieved_chunks}
</참고문서>

<학생정보>   ← 개인화 질문일 때만 삽입
{academic_profile}
</학생정보>
```

---

## 왜 이 순서인가

**규칙 1을 맨 앞에 둔다** — 가장 중요한 제약이고, 프롬프트 앞부분이 더 잘 지켜진다.

**규칙 4(해석 여지)를 넣는 이유** — 학칙은 조문만으로 결론이 안 나는 경우가 있다.
챗봇이 단정해서 학생이 불이익을 받으면 서비스 자체가 문제가 된다.
제안서에서 말한 "행정 불일치로 인한 불이익 차단"은 단정하지 않는 것에서 시작한다.

**규칙 5(숫자)** — 환각이 가장 잘 드러나면서 피해가 큰 지점이 숫자다.
장학금 액수나 필요 학점을 틀리면 답변 전체의 신뢰가 무너진다.

---

## 프롬프트만으로는 부족하다

제약을 걸어도 LLM은 샌다. 그래서 생성 후 **검증 단계**를 별도로 둔다.

```python
# services/verification.py 개요
for 문장 in 답변:
    if 문장이 사실 서술이고 인용이 없으면:
        제거 또는 "행정실 확인 필요"로 대체
```

프롬프트 = 1차 방어, 검증 단계 = 2차 방어.
평가에서 E 유형(답변 불가 질문) 거부율을 재는 이유가 이 두 층이 실제로 동작하는지 확인하기 위해서다.

## sLLM 전환 시 주의

7B~13B 모델은 상용 API 모델보다 지시 준수력이 떨어진다. 전환 시 예상되는 문제:

- 긴 시스템 프롬프트의 뒷부분 규칙을 무시
- 인용 형식을 지키지 않음
- 참고문서에 없는 내용을 그럴듯하게 생성

대응:
- 규칙을 5개 이내로 유지 (지금 뼈대가 5개인 이유)
- 인용은 프롬프트에 맡기지 말고 **후처리로 부착**하는 방안 검토
- 모델 교체 시 평가셋 전체를 재측정. 프롬프트는 모델별로 따로 관리한다.

`configs/prompts/{model_name}/` 구조로 두면 모델별 분기가 자연스럽다.

---

## 버전 관리

프롬프트를 수정하면 평가 결과가 바뀐다. 수정 시:

1. 파일을 고치고 커밋 메시지에 **의도**를 적는다 ("숫자 인용 규칙 추가 — 학점 오답 대응")
2. 평가를 다시 돌리고 결과를 프롬프트 버전과 함께 기록한다

어떤 프롬프트에서 나온 숫자인지 모르면 비교가 불가능해진다.
