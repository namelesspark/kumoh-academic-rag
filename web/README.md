# web — React 클라이언트

금오공대 학사 행정 RAG 챗봇의 **웹 클라이언트**. React 기반 채팅 UI.

API는 [`api/`](../api) 를 호출한다.

---

## 디렉토리 구조

```
web/
├── src/
│   ├── components/
│   │   ├── chat/       # MessageList, MessageBubble, CitationCard, InputBox
│   │   └── common/     # Button, Modal, Spinner 등 공용
│   ├── pages/          # ChatPage, AboutPage
│   ├── hooks/          # useChat, useSession
│   ├── api/            # API 클라이언트 (타입은 API_SPEC.md와 1:1)
│   └── styles/
├── public/
└── docs/
    └── UI_NOTES.md
```

## 화면 설계 원칙

**인용을 숨기지 않는다.**
답변 아래에 근거 조문을 카드로 항상 노출한다. 접어두면 아무도 안 본다.
학생이 원문을 직접 확인할 수 있어야 챗봇 답변을 신뢰할 수 있고, 그게 이 프로젝트가
"규칙 기반 챗봇 대비 나은 이유"를 사용자에게 증명하는 방식이다.

```
┌──────────────────────────────────┐
│ 전과는 2학년 이상, 직전 학기      │
│ 평점 2.5 이상일 때 신청 가능합니다.│
├──────────────────────────────────┤
│ 📄 학사운영규정 제30조(전과) ①    │
│    시행 2025-03-01      [원문 →]  │
└──────────────────────────────────┘
```

**"답변할 수 없음"을 실패처럼 보이게 하지 않는다.**
근거가 없어 답을 못 하는 건 정상 동작이다. 오류 화면이 아니라
행정실 연락처를 담은 정상 메시지로 표시한다.

**학적 연동 여부를 사용자가 매번 통제한다.**
개인화 답변이 필요한 질문에서 토글로 동의를 받는다. 개인정보 조회는 조용히 일어나면 안 된다.

## 개발 예정 순서

1. Vite + React 프로젝트 초기화
2. `src/api/` 타입 정의 — [`api/docs/API_SPEC.md`](../api/docs/API_SPEC.md) 기준
3. mock 응답으로 채팅 UI 완성 (백엔드 없이)
4. 실제 API 연동
5. 인용 카드 / 답변 불가 상태 / 학적 동의 토글

3번을 mock으로 먼저 하는 이유 — 백엔드 완성을 기다리지 않고 병렬로 진행하기 위해서다.
혼자 개발하므로 대기 시간을 만들지 않는 게 중요하다.

---

## 기술 스택 (예정)

- React 18 + Vite
- 상태 관리: 우선 `useState` + Context. 복잡해지면 재검토
- 스타일링: 미정 (Tailwind 유력)

이전 프로젝트(BISKIT POINT)에서 React 비동기 상태 관리로 애먹은 경험이 있어,
채팅 스트리밍/로딩 상태는 처음부터 `useChat` 훅 하나로 모아둔다.
