# 프롬프트 설계

제안서 4단계의 "소스 문서 외 임의 답변 금지" 제약을 어떻게 구현할지 정의한다.
프롬프트는 `configs/prompts/` 에 파일로 두고 버전 관리한다. 코드에 하드코딩하지 않는다.

---

## 시스템 프롬프트 뼈대

```
당신은 국립금오공과대학교 학사 행정 안내 어시스턴트다.

[절대 규칙]
1. 아래 <참고문서>에 포함된 내용만으로 답변한다.
   문서에 없는 내용은 추측하지 말고 "확인할 수 없다"고 답한다.
2. 답변의 모든 사실 서술에는 근거 조문 번호를 명시한다. (예: 학사운영규정 제30조 ①)
3. 참고문서가 비어 있거나 질문과 무관하면, 답변을 생성하지 말고
   해당 부서 연락처를 안내한다.
4. 학칙 해석이 갈릴 수 있는 사안은 단정하지 말고 행정실 확인을 함께 안내한다.
5. 금액·학점·기한 등 숫자는 문서에 적힌 값을 그대로 인용한다. 계산이 필요하면
   calculate 도구를 사용한다.

<참고문서>
{retrieved_chunks}
</참고문서>

<학생정보>   ← 개인화 질문일 때만 삽입
{academic_profile}
</학생정보>
```

---

## 왜 이 순서인가

**규칙 1을 맨 앞에 둔다** — 가장 중요한 제약이고, 프롬프트 앞부분이 더 잘 지켜진다.

**규칙 4(해석 여지)를 넣는 이유** — 학칙은 조문만으로 결론이 안 나는 경우가 있다.
챗봇이 단정해서 학생이 불이익을 받으면 서비스 자체가 문제가 된다.
제안서에서 말한 "행정 불일치로 인한 불이익 차단"은 단정하지 않는 것에서 시작한다.

**규칙 5(숫자)** — 환각이 가장 잘 드러나면서 피해가 큰 지점이 숫자다.
장학금 액수나 필요 학점을 틀리면 답변 전체의 신뢰가 무너진다.

---

## 프롬프트만으로는 부족하다

제약을 걸어도 LLM은 샌다. 그래서 생성 후 **검증 단계**를 별도로 둔다.

```python
# services/verification.py 개요
for 문장 in 답변:
    if 문장이 사실 서술이고 인용이 없으면:
        제거 또는 "행정실 확인 필요"로 대체
```

프롬프트 = 1차 방어, 검증 단계 = 2차 방어.
평가에서 E 유형(답변 불가 질문) 거부율을 재는 이유가 이 두 층이 실제로 동작하는지 확인하기 위해서다.

---

## 근거 판정

지금 앱은 답을 지어내지 않고 검색된 조문을 그대로 인용한다. 그래서 "근거가 약하면
답하지 않는다"는 제약은 프롬프트보다 앞에서, 어느 조문을 답으로 쓸지 고르는 단계에서 지킨다.

검색기(BM25, 낱말이 겹치는 정도로 순위를 매기는 방식)는 질문과 글자 두 개만 겹쳐도
후보를 낸다. `휴학은 몇 학기까지 할 수 있나요?`는 가상 규정과 조사 `까지`만 겹치는데도
제12조의2(별빛 열람 연장)가 1위로 나왔다. 검색기가 추천서를 쓰면 판정 함수가 면접을
한 번 더 보는 셈이다. 판정은 `api/app/services/chat_relevance.py`에 있고,
`api/regulation_app.py`가 문서 한 건짜리 앱과 여러 건짜리 앱에서 검색 함수를 이 판정으로 감싼다.

### 규칙

1. 질문을 줄 단위로 나누고, 줄마다 **핵심 낱말**을 고른다. 전각 글자와 대문자는 같은
   글자로 맞추고 문장 부호는 버린다.
2. 핵심 낱말은 아래를 뺀 두 글자 이상 낱말이다.
   - 조 번호 (`제12조`, `제12조의2`)
   - 묻거나 청하는 말로 시작하는 낱말: 누가·누구·언제·어디·무엇·무슨·뭐·어떻게·어떤·어느·얼마·며칠, 알려·가르쳐·설명해·궁금
   - 물음이나 요청으로 끝나는 서술어: …나요, …가요, …까요, …니까, …는지, …을까, …어요, …해요, …예요, …세요, …죠, …줘 등
3. 남은 낱말 끝의 조사(은·는·이·가·을·를·의·에·까지·부터·에서 등)는 한 번 뗀다.
   떼고 나서 한 글자만 남으면 떼지 않는다. `학과`, `지도`처럼 조사와 같은 글자로 끝나는
   두 글자 낱말을 잃지 않기 위해서다.
4. 조각 본문에서 공백을 지운 글에 그 줄의 핵심 낱말이 **모두** 들어 있으면 통과다.
   항 단위 조각의 본문에는 조 제목도 들어 있다.
5. 핵심 낱말이 없는 줄은 통과하지 못한다. 조 번호만 적은 줄은 조각의 조 번호가 같을 때 통과한다.
6. 한 줄이라도 통과하면 그 조각을 받는다. 사진 질문이 질문과 판독문을 줄바꿈으로 이어
   다시 검색하기 때문이다. 줄을 합쳐서 보면 낱말이 늘어 늘 보류된다.
7. 후보를 검색 순위대로 검사해 처음 통과한 조각을 인용한다. 통과한 조각이 없으면 기존
   보류 문구를 내고 `answered`는 `false`, 인용은 빈 목록이다.

위 목록은 코드에 고정한 상수다. 점수 하한과 동의어 표는 쓰지 않는다. 드문 글자 하나의
점수가 높아 하한으로는 위 오답을 가르지 못하고, 가상 낱말에 맞춘 동의어 표는 실제
규정에서 맞는지 확인할 수 없다.

### 예

| 질문 | 핵심 낱말 | 결과 |
|---|---|---|
| 달빛열람증을 누가 내주나요 | 달빛열람증 | 제3조 인용 |
| 보름날에 별빛 열람실은 언제까지 여나요 | 보름날, 별빛, 열람실 | 제12조의2 인용 |
| 제12조 | 없음 (조 번호만) | 제12조 인용 |
| 휴학은 몇 학기까지 할 수 있나요? | 휴학, 학기 | 보류 |
| 별빛 열람실 휴학 | 별빛, 열람실, 휴학 | 보류 (`휴학`이 없음) |
| 누가 내주나요 | 없음 | 보류 |

### 이 규칙으로 새로 보류되는 질문

규칙은 보류 쪽으로 기운다. 아래 질문은 고치기 전에 답이 나왔지만 이제 보류된다.

- 규정에 없는 낱말이 하나라도 섞인 질문. 다른 낱말이 조문에 있어도 보류한다.
- 같은 뜻의 다른 낱말로 물은 질문 (`빌리다`를 `대출`로). 동의어를 풀지 않는다.
- 묻는 말과 서술어만 있는 질문 (`누가 내주나요`).
- 목록에 없는 어미로 끝난 서술어가 남는 질문. 반말(`언제까지야`)과 활용형(`빌릴 수 있는`)이 그렇다.
- 한 글자 낱말에 조사가 붙은 말(`책을`, `전에`)은 그 글자 그대로 조문에 있어야 한다.
- 검색기가 낸 상위 다섯 후보 안에 통과한 조각이 없는 질문.

조사와 어미를 정확히 떼려면 형태소 분석기(낱말을 뜻 단위로 쪼개는 도구)가 필요하다.
분석 모델을 함께 들여와야 해서 넣지 않았다.

## sLLM 전환 시 주의

7B~13B 모델은 상용 API 모델보다 지시 준수력이 떨어진다. 전환 시 예상되는 문제:

- 긴 시스템 프롬프트의 뒷부분 규칙을 무시
- 인용 형식을 지키지 않음
- 참고문서에 없는 내용을 그럴듯하게 생성

대응:
- 규칙을 5개 이내로 유지 (지금 뼈대가 5개인 이유)
- 인용은 프롬프트에 맡기지 말고 **후처리로 부착**하는 방안 검토
- 모델 교체 시 평가셋 전체를 재측정. 프롬프트는 모델별로 따로 관리한다.

`configs/prompts/{model_name}/` 구조로 두면 모델별 분기가 자연스럽다.

---

## 버전 관리

프롬프트를 수정하면 평가 결과가 바뀐다. 수정 시:

1. 파일을 고치고 커밋 메시지에 **의도**를 적는다 ("숫자 인용 규칙 추가 — 학점 오답 대응")
2. 평가를 다시 돌리고 결과를 프롬프트 버전과 함께 기록한다

어떤 프롬프트에서 나온 숫자인지 모르면 비교가 불가능해진다.
