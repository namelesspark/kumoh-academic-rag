# 서술 규칙

이슈 · PR 본문 · 리뷰 댓글 · 커밋 메시지에 적용한다. 코드 주석과 docstring도 같은 기준을 쓴다.

## 왜 있는 문서인가

이 저장소의 설계 수준은 낮추지 않는다. 바꾸는 것은 설명 문장뿐이다.

읽는 사람은 컴퓨터공학 전공자지만 검색·RAG·웹 인프라 용어에는 익숙하지 않다. 용어가 막히면 설계가 좋아도 검토를 못 하고, 검토를 못 하면 머지 여부를 판단할 수 없다. 검토받지 못한 PR은 쌓여도 진척이 아니다.

## 규칙

### 1. 전문 용어는 첫 등장에 한 줄 설명을 붙인다

바깥에 쉬운 말을 쓰고, 원래 용어는 괄호 안에 남긴다.

- 나쁨 — 자동 검증은 ASGI 콜러블로 직접 호출해 수행한다
- 좋음 — 서버를 띄우지 않고 앱을 파이썬 함수처럼 바로 불러서 확인한다 (ASGI 콜러블 직접 호출)

<!-- -->

- 나쁨 — 조 단위로 청킹하고 메타데이터에 오프셋을 넣는다
- 좋음 — 조문 하나를 검색 단위 하나로 자르고, 그 조문이 원본의 몇 번째 글자에서 시작하는지를 함께 저장한다 (청킹, 문자 오프셋)

### 2. 설명 없이 쓰지 않는 단어

스텁 · 파서 · 오프셋 · 콜러블 · 하네스 · 픽스처 · 루프백 · 직렬화 · 멱등 · 계약 ·
청킹 · 임베딩 · 리랭커 · 재현율 · 인덱싱 · 스키마 · 미들웨어 · 마이그레이션 ·
레이스 컨디션 · 백프레셔 · 아티팩트

목록에 없어도 영문 약어는 전부 첫 등장에 풀어 쓴다.

### 3. 작업 항목은 세 줄로 시작한다

- **무엇을 만드는가** — 한 문장. 비전공자가 읽어도 그림이 그려질 것
- **왜 지금 필요한가** — 한 문장. 어느 작업이 이것을 기다리는지
- **다 됐는지 확인하는 방법** — 복사해서 바로 실행되는 명령 한 줄

상세 설계는 이 세 줄 아래에 쓴다.

### 4. 이슈와 PR 맨 위에 세 줄 요약을 둔다

본문을 읽지 않아도 무엇을 승인하는 것인지 알 수 있어야 한다.

### 5. 구조를 설명할 때 비유를 하나 붙인다

일상 사물에 빗댄다. 한 문단에 하나까지.

> 스텁은 벽에 콘센트를 먼저 박아두는 것이다. 꽂을 가전제품은 아직 없지만
> 규격을 정해두면 나중에 무엇을 사 와도 꽂힌다.

### 6. 금지

- 설명 없는 영문 약어
- 한 문장에 전문 용어 두 개 이상
- 주체를 흐리는 수동태 — 누가 하는지 밝힌다
  - 나쁨 — 검증이 수행된다
  - 좋음 — 협업 도구가 검증 명령을 실행한다

## 바꾸지 않는 것

설계 깊이, 코드 품질, 테스트 범위, 예외 처리 수준은 그대로 둔다.
**쉬운 말로 쓰라는 것이지 쉬운 것을 만들라는 것이 아니다.**

## 완료 판정

이슈를 낼 때 완료 판정에 쓸 명령을 본문에 적는다. 비워두지 않는다.
명령이 없으면 에이전트의 완료 선언을 받아들이지 않는다.

```
python -m unittest core.tests.test_article_parser api.tests.test_health api.tests.test_chat_stub
```
